# J15 Опиши интерфейс и доступ к данным

[← Маршрут](../README.md) · [Назад: J14](j14-integrations.md) · [Дальше: J16 →](j16-specification-changes.md)

**Результат:** поведение экрана, API и разрешений не противоречит друг другу. Ориентир — 16 часов.

Аналитику нужен прототип, чтобы согласовать действия и состояния. Художественная отрисовка необязательна. Для каждого экрана опиши загрузку, данные, пустое состояние, ошибку, валидацию, повтор действия и недоступность функции. Укажи, какие значения вводит человек, какие приходят с backend и какие рассчитываются.

Различай аутентификацию «кто ты» и авторизацию «что тебе разрешено». Роль и владение конкретным объектом проверяются на сервере. Если пользователь подставил чужой bookingId, скрытая кнопка в интерфейсе не защищает данные. В логах и примерах не нужны действующие токены и реальные персональные данные.

**Обязательно:**

- [S76 Forms Tutorial](https://www.w3.org/WAI/tutorials/forms/) · EN. Прочитай подписи полей, инструкции, валидацию и уведомления об ошибках. Перенеси принципы на свой прототип.
- [S62 Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) · EN. Изучи least privilege, deny by default и проверку прав на каждом запросе.
- [S61 OWASP API Security Top 10 2023](https://owasp.org/API-Security/editions/2023/en/0x11-t10/) · EN. Прочитай риск Broken Object Level Authorization и объясни его на чужом bookingId.

**Сделай:** нарисуй три экрана: расписание, мои записи, список участников занятия для администратора. Для каждого перечисли состояния и связь с API. Составь матрицу прав клиент/администратор/внешний сервис. Добавь проверки чтения чужой записи и попытки выполнить административную операцию обычным пользователем.

Отдельно опиши, что увидит клиент после двойного нажатия «Записаться» и потери сети. Временная блокировка кнопки уменьшает число запросов, но сервер всё равно должен обеспечивать согласованные правила повторной операции. Начни с точного описания ожидаемого поведения, затем согласуй механизм с разработчиком.

**Самопроверка:** какие проверки нужны на backend даже при валидации frontend? Можно ли доверять clientId из тела запроса? Что показать при пустом списке? Чем ошибка поля отличается от недоступности сервиса? Какие данные не стоит включать в скриншот дефекта?

**Готово, когда:** по прототипу понятны действия, по матрице — права, а по таблице состояний — поведение при ошибках. Проверка доступа присутствует в сценариях API, а не только в описании интерфейса.
