# J13 Оформи OpenAPI и проверь запросы в Postman

[← Маршрут](../README.md) · [Назад: J12](j12-rest-api.md) · [Дальше: J14 →](j14-integrations.md)

**Результат:** контракт существует в машиночитаемом виде, а примеры запросов можно повторить. Ориентир — 24 часа.

OpenAPI описывает HTTP API: пути, операции, параметры, схемы, ответы и способы авторизации. Swagger — семейство инструментов вокруг спецификации. В этом маршруте фиксируем OpenAPI 3.1.1 как учебную версию; это не заявление о самой новой версии стандарта. Не смешивай её синтаксис с примерами для 3.0 без проверки.

Разбери info, servers, paths, components/schemas, operationId, parameters, requestBody, responses и security. В OpenAPI 3.1 null описывается средствами JSON Schema, например `type: [string, "null"]`; знакомое по 3.0 `nullable: true` не следует переносить механически. Поле required в объекте — список имён обязательных свойств, а required у параметра — отдельный boolean.

**Обязательно:**

- [S38 Проектирование спецификации OpenAPI](https://habr.com/ru/companies/ozontech/articles/825008/) · RU. Прочитай статью и воспроизведи подход на своих методах. Не копируй решения без привязки к кейсу.
- [S34 OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html) · EN. Используй разделы OpenAPI Object, Operation, Parameter, Request Body, Responses и Schema Object.
- [S32 Postman Quick Start](https://learning.postman.com/docs/getting-started/quick-start/) · EN. Пройди первый запрос и изучи коллекции и переменные окружения.
- [S36 Swagger Editor](https://editor.swagger.io/) · EN. Открой YAML, проверь синтаксис и представление контракта. Проверка синтаксиса не заменяет проверку бизнес-логики.

**Сделай:** перенеси методы J12 в один openapi.yaml. Вынеси общие схемы, сделай примеры запросов и ответов, опиши ошибки и безопасность. Импортируй контракт в Postman. Создай переменную baseUrl и запросы на чтение, создание и отмену. Учебный публичный API используй только для освоения инструмента: JSONPlaceholder имитирует изменение данных, а не реализует правила нашего сервиса.

Если собственного backend пока нет, разделяй два результата: коллекция демонстрационных запросов к учебному API и проектный контракт с подготовленными примерами/моками. Не пиши, что бизнес-проверки сервиса прошли на реальном сервере, если сервер отсутствует.

Добавь проверки HTTP-кода, обязательного идентификатора и типа данных. Проверь один ошибочный запрос. Настройки аккаунта и облачного режима Postman могут меняться; для передачи работ достаточно экспортируемых файлов без токенов.

**Самопроверка:** чем схема отличается от example? Почему удачный импорт ещё не доказывает полноту контракта? Где документировать 409? Что меняется при nullable-поле в 3.1? Чем контрактный мок отличается от работающего backend?

**Готово, когда:** YAML разбирается выбранным инструментом, все методы из постановки в нём присутствуют, примеры согласованы со схемами, секретов в экспорте нет.
