# J12 Спроектируй API первой версии

[← Маршрут](../README.md) · [Назад: J11](j11-data-formats.md) · [Дальше: J13 →](j13-openapi-postman.md)

**Результат:** по контракту можно реализовать клиент и сервер, не угадывая основные правила. Ориентир — 24 часа.

REST — архитектурный стиль, HTTP — протокол. Не называй любой JSON поверх HTTP строгим REST. Для практики нам достаточно последовательного ресурсного HTTP API: занятия, записи, их представления и операции. Изучи различие path/query/header/body, безопасных и идемпотентных методов, создания и изменения ресурса, фильтрации и пагинации.

Начни с GET /sessions, GET /sessions/{sessionId}, POST /bookings, GET /bookings/{bookingId}. Для отмены выбери и обоснуй один вариант: отдельное действие или изменение состояния. Не меняй его между документами. Клиентский идентификатор владельца не заменяет проверку прав: принадлежность определяется через доверенный контекст пользователя.

**Обязательно:**

- [S17 Обзор протокола HTTP](https://developer.mozilla.org/ru/docs/Web/HTTP/Guides/Overview) · RU. Повтори методы, заголовки и структуру сообщений.
- [S18 Коды состояния HTTP](https://developer.mozilla.org/ru/docs/Web/HTTP/Reference/Status) · RU. Выбери коды для создания, отсутствия объекта, отказа в доступе и конфликта бизнес-состояния.
- [S38 Проектирование спецификации OpenAPI](https://habr.com/ru/companies/ozontech/articles/825008/) · RU. Прочитай подход к проектированию контракта до реализации. На этом шаге сосредоточься на структуре и согласованности API.

**Расширение:**

- [S73 RFC 9110 HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html) · EN. Точечно прочитай разделы о safe/idempotent и выбранных методах. Идемпотентность относится к ожидаемому эффекту, а не к одинаковому телу ответа.
- [S72 RFC 9457 Problem Details for HTTP APIs](https://www.rfc-editor.org/rfc/rfc9457) · EN. Познакомься со стандартным представлением ошибок. Для проекта можно выбрать упрощённый согласованный формат.

**Сделай:** опиши 5 методов с целью, правами, запросом, успешным ответом, ошибками и примерами. У каждого поля укажи смысл, тип и обязательность отдельно для запроса и ответа. Для списка добавь порядок сортировки, размер страницы, ограничения фильтров и поведение пустой выборки. Для создания — проверку вместимости, дубликата и уже начавшегося занятия.

Составь таблицу ошибок: условие, HTTP-код, бизнес-код, сообщение и действие клиента. Разведи «мест нет», «неверная дата», «нет доступа», «сервис временно недоступен». Не привязывай фронт к тексту сообщения, если для обработки нужен стабильный код.

**Самопроверка:** почему GET не должен создавать запись? Всегда ли повторный POST безопасен? Что означает 202? Чем 404 отличается от пустого списка? Что произойдёт, если клиент отправит неизвестный статус? Зачем контракту сортировка при пагинации?

**Готово, когда:** разработчик может написать обработчик, а QA — позитивные, негативные и граничные проверки. Поведение при конкуренции описано как обязательное правило и передано на техническое согласование, даже если Junior ещё не выбирает механизм блокировок самостоятельно.
