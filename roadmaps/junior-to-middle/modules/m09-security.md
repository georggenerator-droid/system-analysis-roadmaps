# M09 Спроектируй доступ и проверь угрозы

[← Маршрут](../README.md) · [Назад: M08](m08-data-migrations.md) · [Дальше: M10 →](m10-observability.md)

**Результат:** права и доверенные границы описаны на уровне объектов и операций. Ориентир — 20 часов.

Разбери OAuth 2.0 и OpenID Connect, access/refresh/ID token, scopes, роли и объектные разрешения. OAuth решает делегирование доступа, OIDC добавляет идентификационный слой. JWT — формат токена, он не делает содержимое секретным и не заменяет проверку подписи, issuer, audience и срока действия.

Для браузерного и мобильного клиента изучи современную рекомендацию Authorization Code с PKCE по актуальному security BCP. Не выбирай flow по старой статье без проверки. Различай проверку пользователя, клиента и внешнего webhook. CORS — механизм браузера, а не универсальная защита API от чужих вызовов.

**Обязательно:**

- [S58 OAuth 2.0](https://oauth.net/2/) · EN. Разбери actors, scopes, access tokens и основные потоки.
- [S59 How OpenID Connect Works](https://openid.net/developers/how-connect-works/) · EN. Сравни OIDC с OAuth и назначение ID token.
- [S60 RFC 9700 OAuth Security Best Current Practice](https://www.rfc-editor.org/rfc/rfc9700) · EN. Точечно прочитай рекомендации по authorization code, PKCE и небезопасным устаревшим вариантам.
- [S61 OWASP API Security Top 10 2023](https://owasp.org/API-Security/editions/2023/en/0x11-t10/) · EN. Выбери угрозы объектного доступа, аутентификации и ограничений ресурсов.
- [S21 CORS](https://developer.mozilla.org/ru/docs/Web/HTTP/Guides/CORS) · RU. Прочитай назначение CORS и предпроверку.

**Расширение:**

- [S62 Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) · EN. Проверь матрицу разрешений и принцип запрета по умолчанию.
- [S53 Webhooks](https://docs.stripe.com/webhooks) · EN. Разбери проверку подписи callback и повторы.

**Сделай:** нарисуй доверенные границы: клиент, backend, база, worker, внешняя платформа. Опиши получение и использование токенов на уровне контрактов. Составь права на операцию, объект и филиал: администратор одного филиала не должен автоматически видеть всех клиентов сети.

Проведи разбор 8 угроз: чужой bookingId, подмена branchId, административная команда обычным токеном, повтор подписанного callback, просроченный токен, массовое создание удержаний, секрет в логе, избыточные данные в событии. Для каждой укажи контроль и проверку. Нормативные требования конкретной отрасли согласуются со специалистами безопасности; этот блок не заменяет аудит.

**Самопроверка:** откуда сервер узнаёт владельца? Можно ли ID token отправлять любому API как access token? Как защитить повтор callback? Почему роли недостаточно без проверки филиала? Где нужна маскировка? Что остаётся доступным после отзыва прав?

**Зачёт:** угрозы связаны с конкретными полями, методами и тестами. Нет утверждения «безопасно, потому что HTTPS/JWT» без остальных проверок.
