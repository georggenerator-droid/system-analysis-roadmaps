# M05 Меняй API без неожиданностей для клиентов

[← Маршрут](../README.md) · [Назад: M04](m04-transactions-concurrency.md) · [Дальше: M06 →](m06-event-driven-integration.md)

**Результат:** изменение контракта учитывает действующих потребителей и повторные команды. Ориентир — 22 часа.

Разбери backward compatibility, версионирование, deprecation, optional/required, null/absence, новые enum-значения, пагинацию при изменяемых данных и контрактные проверки. Даже добавление поля может сломать строгого клиента, а новое значение enum — код с закрытым перечнем. Совместимость проверяется на конкретном потребителе, а не объявляется по интуиции.

Опиши идемпотентность команд: область ключа, связь с пользователем и операцией, срок хранения результата, сравнение payload, параллельные повторы и ответ после сбоя. Заголовок с названием Idempotency-Key сам по себе ничего не гарантирует. Контракт должен объяснять поведение, а реализация — обеспечивать его атомарно с эффектом команды либо согласованной моделью восстановления.

**Обязательно:**

- [S39 Как мы ломали и собирали API заново](https://habr.com/ru/companies/sberbank/articles/937218/) · RU. Разбери последствия изменения API в нескольких командах. Составь свой список потребителей и точек согласования.
- [S52 Idempotent requests](https://docs.stripe.com/api/idempotent_requests) · EN. Посмотри, как конкретный API описывает идемпотентные запросы. Не переноси срок хранения и детали Stripe как универсальный стандарт.
- [S34 OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html) · EN. Проверь совместимость схем, обязательность, enum и описание ошибок в своей OpenAPI 3.1.1.

**Расширение:**

- [S68 Consumer Driven Contracts](https://martinfowler.com/articles/consumerDrivenContracts.html) · EN. Прочитай подход к контрактам, исходящим из ожиданий потребителя.
- [S69 Pact Introduction](https://docs.pact.io/) · EN. Узнай, как Pact связывает проверку consumer и provider; писать инфраструктуру тестов аналитику необязательно.

**Сделай:** добавь удержание к API, сохранив поведение старого клиента через явный адаптационный сценарий. Подготовь таблицу v1/v2: поведение, поля, ошибки, срок поддержки и способ проверки. Опиши 8 повторов: одинаковый ключ/одинаковое тело, одинаковый ключ/другое тело, два одновременных запроса, другой пользователь, потерянный ответ, истёкший ключ, операция в обработке и повтор после неуспешного результата.

Отдельно сравни offset и cursor pagination для расписания, в которое добавляются занятия. Фиксируй стабильный порядок и дополнительный ключ при равных датах. Наличие курсора не гарантирует стабильный снимок без дополнительного решения.

**Самопроверка:** что является ломающим изменением? Как клиент узнает о deprecation? Можно ли дедуплицировать только по телу запроса? Что произойдёт при сохранении ключа до бизнес-эффекта и сбое между ними? Почему новый enum надо согласовать с мобильным клиентом?

**Зачёт:** есть diff контракта, матрица потребителей, сценарии повторов и план перехода. Старый клиент проверяется отдельно, а не предполагается совместимым.
